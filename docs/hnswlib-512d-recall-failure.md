# hnswlib 在 512 维 BGE 向量上召回不足的完整诊断记录

> 日期：2026-08-08
> 硬件：Orange Pi 4 Pro（A733 SoC，2×A76 + 6×A55，Debian 12）
> 场景：个人 Agent 的语义记忆检索加速，尝试用 hnswlib HNSW 替代 sqlite-vec 暴力 KNN，最终因召回不足弃用，改用 numpy 内存暴力精确检索。
> 目的：完整记录诊断过程与数据，供他人参考，避免重复踩坑。

---

## 1. 背景

Agent 的向量检索层使用 sqlite-vec 虚拟表做暴力 KNN：

| 表 | 行数 | 维度 | 说明 |
|---|---|---|---|
| memories_vec | 2,129 | 512 | 记忆向量 |
| memories_child_vec | 11,400 | 512 | 记忆子块向量 |
| kg_entities_vec | 17 | 512 | 知识图谱实体 |
| kg_relations_vec | 215 | 512 | 知识图谱关系 |

- embedding 由 BGE-small-zh-v1.5 生成（512 维），全部 **L2 归一化**（norm=1.0）
- sqlite-vec 返回 **L2 欧氏距离**（`sqrt(sum((v-q)^2))`），默认度量
- 暴力 KNN 实测 **33.5ms/次**（主要开销是 JSON 反序列化 + 逐行距离计算）
- 检索数据中 **36% 是重复向量**（11,400 条中仅 7,333 条唯一，934 个向量各出现 2+ 次）

目标：把检索从 33.5ms 降到 1ms 级，且 top-10 结果与暴力 KNN 重合率 ≥98%。

## 2. 方案选择与实现

选型 hnswlib 0.8.0。板端 aarch64 `pip install` 直接编译成功（g++ 12.2.0）。

实现了一个多表 HnswIndex 封装：

- `init_index(max_elements, M=16, ef_construction=200, allow_replace_deleted=True)`
- 增量 upsert：`mark_deleted` + `replace_deleted`（hnswlib 不支持原地覆盖，必须走删除-替换流程）
- filter 回调实现 `candidate_ids`（只在指定 rowid 集合内检索）
- `save_index` / `load_index` 持久化；`resize_index` 自动扩容
- 检索质量参数：`ef_construction=200`、`M=16`、`set_ef(200)`

独立验证结果（**速度非常好**）：

```
全量加载（11,400 条构建）: 8.7s
检索: 0.45ms/次  ← 比暴力 33.5ms 快 74 倍
save/load 一致: 通过
增量 upsert/delete: 正确
```

## 3. 问题：召回率不达标

四表初测（扰动查询 top-10，与 sqlite-vec 暴力结果对比 rowid 集合重合率）：

| 表 | 重合率 |
|---|---|
| memories_vec | 99.5% |
| **memories_child_vec** | **69.15%** |
| kg_entities_vec | 100% |
| kg_relations_vec | 100% |

只有 memories_child_vec（11,400 条，最大的表）严重不达标。

## 4. 系统性诊断（逐步排除）

### 4.1 ef 调参无效

ef 从 64 一路调到 1024（远超常规）：召回仅从 70.7% → 76.1%。**提升微不足道**。
HNSW 的 ef 是"搜索深度"，如果 ef=1024 还补不齐，说明问题不在贪心搜索的广度。

### 4.2 去重对照无效

怀疑 36% 重复向量干扰，做四组对照（all=11,400 条 / uniq=7,333 条 × M16/M32）：

```
all  M16 ef200: avg_jaccard=0.7150
all  M32 ef400: avg_jaccard=0.7590
uniq M16 ef200: avg_jaccard=0.6820
uniq M32 ef400: avg_jaccard=0.6860
```

去重反而更差。排除重复向量因素。

### 4.3 距离度量协议陷阱（重要）

排查中发现三个"距离"协议不一致，容易误判：

| 来源 | 返回值 | 关系（归一化向量） |
|---|---|---|
| sqlite-vec | `sqrt(L2²)` | 欧氏距离 |
| hnswlib l2 空间 | `L2²` | 平方距离 |
| hnswlib cosine 空间 | `1 - cos` | = L2²/2（归一化后） |

三者对同一批数据**排序单调等价**——所以距离数值不同并不影响召回对比。
结论：距离度量不是召回低的原因，但**对比结果时必须统一协议**，否则会得出错误结论。

### 4.4 宽召回 + 精排（rerank）补不齐

怀疑是"排序正确但集合缺失"，做宽召回 + numpy 精排：

```
CAND=20:  avg_jaccard=0.7725 exact=94/200
CAND=50:  avg_jaccard=0.7270
CAND=100: avg_jaccard=0.7265
CAND=200: avg_jaccard=0.7265
```

把候选从 20 扩到 200，召回纹丝不动（~73%）。**rerank 补不齐 → HNSW 图里根本没把这些正确节点作为邻居/候选**。

### 4.5 随机数据对照实验（定位根因）

用完全相同的方法跑随机数据：

```
random-8000x512:        avg_jaccard=0.8360 exact=15/100
random-8000x512-l2norm: avg_jaccard=0.8320
bge-11400x512:          avg_jaccard=0.0860（argpartition 位置索引干扰，真实约 73%）
```

随机数据的 ANN 召回 83.6% vs 真实 BGE 向量 ~73%。**同样的算法、同样的参数，随机数据召回明显更好 → 问题出在数据分布本身，不是实现**。

## 5. 根因分析

真实 BGE 向量的特性：

1. **512 维高维空间**：维度灾难，距离分布集中在很小的区间，最近邻与次近邻距离差异微小
2. **向量相似度高度集中**：BGE 生成的语义向量彼此相似度高，内积/距离区分度低
3. **大量重复向量**：同一语义被多次存储（不同时间/上下文），graph 中大量等距节点

HNSW 的贪心图搜索在"高维 + 区分度低 + 等距节点多"的数据上，**先天无法保证召回**——这不是参数能解决的，是算法与数据分布的适配问题。

## 6. 最终方案：numpy 内存暴力

放弃 ANN，回到精确暴力，但搬进内存 + numpy/BLAS 向量化：

- 11,400×512 float32 = **23.3MB 常驻内存**（板端内存充足）
- 检索公式：`dist² = ||data||² + ||q||² - 2·data·q`（预计算每行 `||data||²`）
- `np.argpartition` 取 top-k（O(n) 选择，无需全排序），稳定排序修正顺序
- 结果：**4.5ms/次**（vs SQLite 33.5ms，快 ~7 倍；BLAS 点积为主）
- **与 SQLite 距离多重集 100% 一致**（同样的 L2 度量、同样的真实 top-k）

回归验证（200 条扰动查询 × 4 表）：

| 表 | 距离多重集一致率 | 说明 |
|---|---|---|
| memories_vec | 100% | 无差异 |
| memories_child_vec | 100% | 57/200 查询 rowid 集合不同，但**全部是等距平局取行差异**（重复向量导致），距离零偏差 |
| kg_entities_vec | 100% | |
| kg_relations_vec | 100% | |

> 关键认知：`rowid 集合 100% 重合` 在存在大量重复向量时**不可能达成**——等距离的行谁先谁后没有客观标准。正确的验收标准是**距离多重集一致**（top-k 的 k 个距离完全相同）。

零额外依赖（numpy 已在环境），失败自动回退 SQLite，可全量重建。

## 7. 经验总结

1. **ANN 召回验收不能只看速度**。0.45ms 的检索如果召回只有 73%，等于让 Agent 在 27% 的时间里"忘记"了正确的记忆——对于记忆系统这是不可接受的。
2. **先测数据分布，再选算法**。在投入 ANN 之前，先回答：向量区分度如何？重复率多高？维度多高？随机数据对照实验是定位"实现问题 vs 数据问题"的最快手段。
3. **参数调优要有边际收益意识**。ef 从 64→1024 召回只涨 5%，就该停下来怀疑方向。
4. **rerank 是召回的下游，不是补丁**。如果宽召回（CAND=200）都补不齐，说明候选集本身是残缺的，rerank 无能为力。
5. **距离协议必须统一**。sqlite-vec / hnswlib-l2 / hnswlib-cosine 返回三种不同的数值，排序等价但数值不同，对比前必须换算，否则会得出"距离不一致 = 结果错误"的假结论。
6. **重复向量下，验收标准要定义正确**。等距平局时 rowid 集合不可能 100% 重合，用"距离多重集一致"或"Jaccard 集合重合"配合距离检查才是合理的。
7. **在数据量可承受时，精确暴力 + 向量化是性价比之王**。23MB 内存换 7 倍加速 + 100% 精确，比 ANN 的调参地狱（M/ef/去重/距离/rerank 全部试过）划算得多。数据量到百万级再考虑 ANN 才是正确的时机。

## 8. 结论

hnswlib 本身实现正确、性能出色（0.45ms），但**在 512 维 BGE 语义向量 + 36% 重复 + 高相似度集中的数据分布下，HNSW 贪心图搜索的召回率天花板 ~73%**，无法达到 98% 验收标准。最终采用 numpy 内存暴力精确检索（4.5ms，距离 100% 对齐 SQLite），问题彻底解决。
